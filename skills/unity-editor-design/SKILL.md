# Unity 编辑器工具设计

目标是做出经过设计的桌面工具，而不只是把原生控件排整齐。保留 Unity 的操作习惯与技术约束，**不把默认灰色皮肤、没有遮挡或编译通过当成审美合格**。

当前为实验性辅助。两组独立有/无 skill 小样本没有证明稳定审美增益，见 [验证范围](references/validation.md)。实现任务应包含实机看图和修订，不能因加载了它就声称结果好看。

## 读取范围

先看目标窗口的截图、代码、已有样式和用户给的参考。遵守当前项目的 AGENTS.md、文档入口和目标目录约定；不要假设项目存在本 skill 开发时的目录、工具或规则。下列路径均相对于本 skill 所在目录，而不是当前工作目录。

- 设计或审美审查：读 [references/visual-direction.md](references/visual-direction.md)，选与目标相关的参考，不每次重读所有来源。
- 字体、字重、背景或配色是主要诉求时，先读 [references/type-and-color-recipes.md](references/type-and-color-recipes.md)，用同一组复杂数据比较文字体系与表面颜色，不只换强调色。
- 写代码或 USS：再读 [references/unity-adaptation.md](references/unity-adaptation.md)。文字校准或自定义控件状态有问题时，读 [references/typography-and-states.md](references/typography-and-states.md)。
- 看实机样例：[examples/complex/README.md](examples/complex/README.md)。包含三栏、密集数据、多选和冲突，但它不是默认布局，也不要只照抄颜色。
- 核对开源来源、改编和许可：[references/sources.md](references/sources.md)。

## 1. 先判断什么使这个界面显得粗糙

区分需求：仅建议/审查、修改现有工具、独立演示。仅建议时不擅自写代码、启动编辑器或创建演示。

确认任务、用户、数据量、Unity 版本、UI 技术和允许修改的部分。保留业务行为；已有 IMGUI 不自动重写 UI Toolkit。

看原图时优先找三个最影响观感的问题，而不是从控件 API 开始：

- 所有文字和按钮是否同等醒目，视线没有重点？
- 顶部是否被多层工具条切碎，底部是否散落很多说明？
- 有无比例失衡的留白、挤压主要内容的副列、过多框线？
- 主操作是否像禁用按钮，默认控件和自定义区是否互相冲突？

**完成条件：**用具体视觉事实描述问题和需要保留的行为。不要只写“缺少高级感”，也不以主观形容词代替定位。

## 2. 建立视觉方向，而不是先列禁令

优先看用户或项目已有界面图，再选 1–2 个成熟桌面工具的相关局部。文章文字只能支持设计原则，不能代替视觉依据。外部图片不可得时，明确限制并继续从实际任务设计，不反复搜索、停工等待，也不假装已经看过。借鉴的是比例、分组、文字、表面层次和交互，不是复制品牌或把网页 Hero 放进编辑器。Unity Foundations 是约束参考，不是要求所有窗口长成默认 Inspector。

写一个很短的视觉方案：

- **结构：**主要数据占什么位置，导航/输入/结果/操作如何分开。
- **层级：**标题、正文、辅助文字的大小/字重/颜色如何区分。
- **表面：**导航、内容、输入三类区域如何区分；强调色放在哪里。
- **节奏：**行距、组距、边距及控件高度怎么配合，而不是各自取数。

重大改版且方向未定时，先比较两种明显不同的布局或局部样稿；不要只换主题色冒充两个设计。不为已有明确参考的窄改动强制增加方案。

**完成条件：**能说出用户将在截图里看到的三项变化及其依据。只有“原生、简洁、克制、少装饰”不够，它们无法决定画面。

## 3. 用正向设计手段建立品质

- **文字先校准再分层。** 用真实中英混排、数字、长路径在标题/正文/输入框里渲染，检查字面高度、基线、行框和灰度，记录字体/回退及缩放的已知情况。独立窗口与 Inspector 分别定尺度；不要只调字号，或把所有文字锁在 12px。
- **空间有分工。** 组内靠近、组间拉开；列表需要稳定节奏，操作区需要一眼辨认。不要用缩字或随意加大行高掩盖结构问题。
- **表面有层次。** 少量中性背景明确导航、主内容、输入；边界该靠背景差时就不再加框线。允许为共同操作建立容器，不机械禁止卡片、圆角或颜色。
- **操作有主次且可用状态明确。** 主操作强调、次操作安静，不等于次操作要灰得像禁用。把启用/禁用控件并排比较，核对文字对比、底色、边框；高度、内边距、圆角和各状态成套设计。动作与其对象保持视觉关联，不能一律塞到远处底栏。保留原生 Button 行为，不必保留默认外观。
- **信息有形状。** 类型图标帮助辨认资源，路径弱于名称，数值右对齐；状态标签只在状态确需强调时使用。不用每行重复按钮或装饰徽章填空。
- **视觉变化有原因。** 选中、焦点、警告分别表达；动画只解释操作反馈。没有动效不等于完成设计，有动效也不等于精致。

**完成条件：**标题、主要内容、主操作形成清楚顺序；同类控件表现一致；去掉任何装饰或规则都能说明画面会改善还是变差。

## 4. 在 Unity 中实现同一套视觉语言

优先使用原生控件的选择、焦点、滚动与虚拟化能力；按目标版本调整 USS 或集中样式。**原生行为和默认外观是两件事。** 不用一排 Label 假装 ListView，也不因为原生控件可用就放弃视觉设计。定制页签/按钮时核对默认底图、边框、样式优先级及实际边界，检查默认、hover、pressed、focus、selected、disabled及叠加状态；不能只覆盖背景色。

默认沿用项目主题；定制视觉时允许集中定义深浅调色板和语义样式。不要散落固定颜色，不要假设 USS 支持所有 CSS 属性。验证原生控件与自定义面板是否协调。

窗口缩小时优先调整布局：隐藏低频摘要、减少副列、调整分栏或让数据区滚动；不让主要按钮被挤出窗口。长文件名需要完整读取入口，也要保证日常扫读不能全靠 tooltip。

批处理预览、选择和执行范围必须一致。演示用假数据、模拟操作；未经业务实现，不宣称已经检查实际文件冲突、权限或导入规则。

**完成条件：**同一视觉方向在正常和最小支持尺寸都成立；不是宽图好看、窄图只勉强没重叠。

## 5. 分开审美评审和工程验证

### 仅建议/审查

交付主要问题、明确改法、保留行为和待验证项，止于用户要求。

### 实现/演示

工程检查：编译、主要状态、深浅配色、正常/窄窗口、长文本、空态和阻止态。只测受影响组合，不机械全排列。大改版或技能示例用一屏代表性密集数据，并包含多选/混合状态、详情与冲突；不能拿几条短名称和空白默认页证明字体/配色在复杂工具里成立。

审美检查：看实际渲染图，与修改前和参考放在同一尺寸对比，分别回答：

1. 第一眼看到什么？是否与任务一致？排错工具应先看诊断，数据工具先看对象；不能用醒目标题补偿任务内容太弱。
2. 文字、间距、比例、表面与组件细节，哪几项比原版具体变好？
3. 是否仍像随手拼出的默认控件列表？最明显的三个短板是什么？

用户要求独立 review 时，让另一个 agent 先看截图、不看测试通过数量；要求其可以判“审美不通过”。不要给“已完善、已符合规范”的前置结论。主 agent 核对、修复后重新截图。

**完成条件：**有真实前后对照和具体变化；报告剩余短板，不用功能通过数量证明好看。若 reviewer 只说“无溢出、可读”，审美检查还没完成。

## 交付

先展示结果图，再简述视觉改动和验证边界。保留可打开的例子和旧图，不要求用户先读长报告来判断好不好看。

HTML 效果图标为原型，不能称 Unity 截图。在深色 Editor 里切换自定义浅色面板，不等于已经验证真实浅色 Editor。说明实际测试尺寸、主题以及停靠、高 DPI、键盘等未测项。

示例是反例/样例，不是默认模板；新任务不应自动复制它的侧栏、配色和标题。维护本 skill 时，以独立新上下文在未见任务上的实际产出为证据；同任务有/无 skill、同数据/环境/预算，盲审截图，功能检查另记。不能用作者在本会话手工修好的演示证明跨会话效果。评测方法与现有证据见 [references/validation.md](references/validation.md)。

这个 skill 不决定业务逻辑、资源命名制度或服务端规则，也不能自封审美验收通过；用户对最终方向的判断优先。
